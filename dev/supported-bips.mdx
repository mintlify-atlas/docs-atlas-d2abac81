The table below lists every specification that Bitcoin Wallet implements. Partially supported or deliberately unsupported proposals are described separately.

<Note>
  These lists are not exhaustive. bitcoinj may implement additional specifications that Bitcoin Wallet inherits implicitly.
</Note>

## Partially supported or deliberately unsupported

### BIP-44 — Multi-account hierarchy for deterministic wallets

[BIP-44](https://github.com/bitcoin/bips/blob/master/bip-0044.mediawiki) is **deliberately not supported**.

BIP-44 requires wallets to support multiple accounts per seed phrase. Bitcoin Wallet instead uses BIP-32 with a single account by design, to keep the user experience simple.

<Warning>
  Wallets derived from BIP-32 and BIP-44 are **not interchangeable** even for the same seed phrase. If you import a Bitcoin Wallet seed into a BIP-44-compatible wallet (or vice versa), you will see a different transaction history and different addresses.
</Warning>

### BIP-72 — `bitcoin:` URI extensions for payment protocol

[BIP-72](https://github.com/bitcoin/bips/blob/master/bip-0072.mediawiki) is **partially supported**.

The spec recommends that wallets ignore the address, amount, label, and message fields in the URI when a `request` parameter is present. Bitcoin Wallet does **not** follow this recommendation. Instead, when you use the `request` parameter, you must do one of the following:

1. Supply an `address` and optionally an `amount` whose values exactly match the corresponding fields in the linked `PaymentDetails` message. The linked payment request must contain exactly one output, and that output's script must be one of: `pay-to-pubkey`, `pay-to-pubkey-hash`, `pay-to-witness-pubkey-hash`, or `pay-to-script-hash`.

2. Supply an `h` parameter containing the unpadded Base64URL-encoded SHA-256 hash of the linked payment request bytes.

If neither condition is met, the linked payment request is rejected.
